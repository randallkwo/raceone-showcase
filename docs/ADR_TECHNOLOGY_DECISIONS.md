# RaceOne — Architecture Decision Records (ADR)

> 這份文件記錄 RaceOne 平台在開發過程中做出的關鍵架構決策，以及**為什麼**選擇這個方案。
> 每則 ADR 呈現：背景 → 選項 → 決策 → 理由 → 後果。
> 不含任何商業邏輯、權限設定或部署金鑰等實施細節。

---

## ADR-001：使用共享 Schema + Row-Level Security 做多租戶隔離

**狀態**：已採用 (2026-08) · **領域**：資料庫架構

### 背景
RaceOne 要從單一賽事系統轉型為多租戶白牌平台，需決定資料隔離方式。

### 考慮過的選項
| 選項 | 隔離度 | 成本 | 遷移成本 |
|------|:------:|:----:|:--------:|
| A. 每租戶獨立資料庫 | 最高 | 高 | 高 |
| B. 共享 DB + 共享 Schema + Row-Level 隔離 | 中高 | 低 | 低 |
| C. 共享 DB + 每租戶獨立 Schema | 高 | 中 | 中 |

### 決策
選擇 **選項 B：共享 Schema + RLS 隔離**。

### 理由
1. **成本最低**：單一 Supabase 專案，不需為每租戶開 DB/Schema
2. **遷移負擔最小**：既有單一租戶資料幾乎不用搬移
3. **彈性**：未來若需升級隔離度，可平滑過渡到 C 或 A，不影響業務邏輯
4. **資料庫層即強制**：RLS 讓權限是資料層的約束，而非業務邏輯的 if/else

### 後果
- 正面：單一 DB 維護成本、ORM 查詢相容、SQL 可移植
- 代價：RLS Policy 需謹慎設計（見 RT-01 安全架構），查詢需注意索引以免效能退化

## ADR-002：權限控制採用「三層防禦」而非單一層

**狀態**：已採用 · **領域**：安全架構

### 背景
多角色後台需要管控不同使用者能看什麼、能操作什麼。

### 決策
採用 **Middleware（路由守衛）+ UI 權限（元件隱藏）+ Database RLS（資料強制）** 三層。

### 理由
| 考量 | 單一層(僅 UI) | 三層防禦 |
|------|:-----------:|:--------:|
| 安全失敗點 | 1 個（可被繞過） | 3 個（層層把關） |
| 使用者體驗 | — | UI 層先隱藏，避免點擊後才被擋 |
| 最後防線 | 無 | Database RLS 無法繞過（即使直連 DB） |

### 後果
- UI 層純做 UX（隱藏），不當安全依據
- DB 層是最後防線，任何查詢（含工具直連）都受限
- 建置成本較高，但大量降低日後安全性意外

## ADR-003：以統一的 Message 抽象層整合多通訊平台

**狀態**：已採用 · **領域**：即時通訊架構

### 背景
LINE / Telegram / Discord 三平台的 API 格式、回覆機制、群組標識皆不同，業務要能在三平台運作。

### 選項
A. 每個平台各寫一套獨立邏輯
B. Adapter Pattern：統一 `Incoming/OutgoingMessage` 抽象 + 每平台一個 Adapter

### 決策
選擇 **選項 B：Adapter Pattern 統一抽象層**。

### 理由
1. 業務邏輯只寫一次，不因平台重複（消除 ×3 的成本）
2. 新增平台（如 Discord）只需新增一個 Adapter，其餘不動
3. 統一模型讓測試、審計、擴充一致

### 後果
- 正面：維護成本大幅下降、擴充容易
- 代價：需為平台專屬能力（快捷回覆、鍵盤、Embed）保留擴充點（`options` / `rawEvent`）

## ADR-004：指令採用「資料驅動」而非「程式碼硬編碼」

**狀態**：已採用 · **領域**：可設定性 / 低程式碼

### 背景
賽事主辦方希望自行新增 Bot 指令（如「查報名進度」「補給站公告」），不想每次請求工程師改 code、重新部署。

### 決策
指令**存於資料庫**（如 `bot_commands` 表），由通用 handler 依資料列動態載入執行；支援「靜態範本」與「LLM 動態生成」兩種模式。

### 理由
1. 非工程師可透過管理後台新增指令，免改 code
2. 「熱載入」：資料變更即生效，免重啟部署
3. 指令清單集中管理、可啟停、可排序、可配權限

### 後果
- 正面：主辦方自助、系統彈性大增
- 代價：需設計指令的 schema、權限、變數替換規範；需在「內建指令」與「自訂指令」間定義優先順序

## ADR-005：金流/外部服務以「可插拔/可模擬」設計

**狀態**：已採用 · **領域**：外部整合

### 背景
平台需串接金流（綠界 NeWebPay）、Email (Resend)、Notion 等外部服務，且需要有可獨立測試的環境。

### 決策
所有外部整合皆透過**環境變數開關**控管，支援「真實模式」與「模擬模式」（如 `MOCK_PAYMENT_WEBHOOK=true`）；Demo 環境可完全停用外部服務，僅記錄日誌。

### 理由
1. Demo / 測試環境不需真實金流或發真實通知，避免副作用
2. 相同的 codebase 可透過 env 切換模式，不需 fork
3. 外部服務暫停時系統仍可運作（降級）

### 後果
- 正面：可獨立測試、Demo 安全、外部服務故障不阻斷核心功能
- 代價：需額外的模式判斷邏輯與 mock 實作

## ADR-006：採用「Release QA Gate」作為品質門檻

**狀態**：已採用 · **領域**：開發流程 / CI

### 背景
平台功能多、滅單錯誤影響使用者體驗與賽事安全性，需要一套可重複、可信賴的部署前品質檢查。

### 決策
建立 **Release QA Gate**——一組可自動執行的檢查項，任何變更要觸發 production 前必須全部通過：

- Build 成功（無 TS/lint error）
- 公開頁面回傳 200
- 受保護頁未登入回傳 307
- 資料庫表格齊全
- Middleware 路由正確
- 使用者模擬（訪客 / 後台 / 跑者自助）全通過
- 無已知高優先 bug

### 理由
1. 把「靠感覺」改為「可複製、可稽核」的流程
2. 大量降低誤上錯版、靜默失敗
3. 自動化（含 Browserbase 模擬）可重複執行，不依賴個人記憶

### 後果
- 正面：品質穩定、每次 release 有共同標準
- 代價：需維護測試腳本與模擬流程，偶有誤報需人工判斷
