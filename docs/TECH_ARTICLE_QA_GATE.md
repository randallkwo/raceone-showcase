## 1. 開場：為什麼「靠感覺」的 release 會出事？（~300 字）

### Hook
> 「很多 side project 或小團隊的發布流程是這樣：開發者跑一下 `pnpm build`，覺得『應該沒問題』就推上線了。但 production 最容易出事的，往往不是 build 失敗，而是**功能在特定情境下壞掉**——某人沒登入就看到管理人頁面、某個 API 未驗證就回傳資料、某個表單送出去就 500。RaceOne 賽事平台出錯的代價不只是難看，而是**影響賽事營運**。所以我們建立了一套 Release QA Gate：在每次變更要觸發 production 前，七項檢查必須全部通過，把『靠感覺』變成『可稽核』。」

### 背景
- RaceOne 是 Next.js 14 + Supabase 的平台，功能多（報名/財務/賽日營運/Bot）
- 需要一套可重複、可信賴的部署前品質把關

---

## 2. 問題：部署前的「最後一哩」不可靠（~300 字）

### 2.1 常見的發布痛點

| 問題 | 後果 |
|------|------|
| 只跑 build 就上線 | 繞過「頁面真的打得開嗎」「未登入會不會被擋」 |
| 靠開發者記憶 | 每次漏檢查的項目都不同，無法累積 |
| 人工點測 | 流程繁瑣、易漏、無法重複 |
| 沒有回歸機制 | 改 A 壞 B，且沒人發現 |

### 2.2 賽事平台特有的風險
- 報名/財務資料錯誤影響真實使用
- 未登入外洩管理資料是嚴重資安事件
- 賽日營運故障直接影響現場

> **核心需求**：一套**可自動執行、可稽核、每次 release 都跑**的檢查，而不是依賴人。

---

## 3. Release QA Gate：把品質變成一組可稽核的檢查（~400 字）

### 3.1 定義

Release QA Gate = 一組在**變更要觸發 production 前**必須全部「綠燈」的檢查項，任一失敗即阻止 release。

### 3.2 為什麼能提升品質

| 面向 | 傳統（人工） | QA Gate |
|------|:-----------:|:-------:|
| 完整性 | 憑記憶、易漏 | 固定清單 |
| 可重複 | 每次不同 | 每次相同 |
| 可信賴 | 主觀 | 可稽核（log + 通過/失敗） |
| 累積性 | 無法累積 | 累積成工程資產 |

## 4. 七大檢查項實作（~600 字）

RaceOne 的 QA Gate 包含以下檢查（採 `run-tests.sh` 執行）：

### ① Build 成功
```bash
pnpm run build  # 確認無 TS / lint error
```

### ② 公開頁面 HTTP 200
```bash
for path in "/" "/events" "/news" "/login"; do
  code=$(curl -s -o /dev/null -w '%{http_code}' "$DOMAIN$path")
  # code 應為 200
done
```

### ③ 受保護頁面未登入 → 307
```bash
for path in "/dashboard" "/races" "/registrations"; do
  code=$(curl -s -o /dev/null -w '%{http_code}' "$DOMAIN$path")
  # code 應為 307（跳登入）
done
```

### ④ 資料庫表格齊全
```python
# 用 service role 對每個核心表發 REST count 查詢
# 全部回 200（表示表存在、可存取）
tables = ['race_events', 'registrations', 'transactions', ...]
```

### ⑤ Middleware 正確
```bash
# 確認公開路徑被排除、受保護路徑被攔
grep -qE "公開路徑 regex" src/middleware.ts
```

### ⑥ 未登入 API 保護（防外洩）
```bash
# 未登入存取管理 API 應回 401
for ep in "/api/users..." "/api/users/set-password"; do
  code=$(curl -X POST "$DOMAIN$ep" -H 'Content-Type: application/json' -d '{}')
  # code 應為 401
done
```

### ⑦ 表單健壯性稽核（try/finally + disabled）
```bash
# 每個 mutation 表單需有 try/finally + 送出按鈕 disabled
# 避免送出時崩潰、重複送出
grep -c "finally\s*{" "$file"
grep -cE "disabled=\{.*(loading|saving|submitting)\}" "$file"
```

> **每一項都是「使用者真的會遇到」的品質維度**，而非追求覆蓋率的象牙塔指標。

## 5. 使用者模擬（Browserbase）作為最高層級驗證（~400 字）

### 5.1 為何需要真瀏覽器模擬
前面的 curl 只能驗證「HTTP 狀態碼」，但**使用者實際在瀏覽器上是否能看到正確內容、操作是否正常**，需要真瀏覽器模擬。

### 5.2 三類使用者模擬流程

```bash
# A. 公開訪客（7 頁）
#    首頁 / 賽事列表 / 賽事詳情 / 成績 / 公告+內文 / 登入頁

# B. 後台管理（8 頁）
#    dashboard / races / 賽事詳情+報名 tab /
#    registrations / users / budget / transactions / sponsors

# C. 跑者自助（3 流程）
#    我的報名 / 我的成績 / 個人資料編輯
#    （登入 → 操作 → 登出）
```

### 5.3 逐頁檢查錯誤字串
每一頁模擬後，掃描頁面是否存在「使用者可見錯誤」：

```bash
ERROR_STRINGS="找不到此賽事|error|Unexpected end of JSON input|500|Cannot|Failed"
```

> **誤報注意**：某些 CSS/JS 可能含 'error' 字樣，需人工確認是否為「使用者可見錯誤」，因此 QA Gate 仍保留人工判斷。

## 6. 與 CI/CD 整合：自動化守門（~400 字）

### 6.1 跑在每次部署前

```
開發者 commit/push
      │
      ▼
CI 執行 Release QA Gate（build + HTTP + DB + Middleware + 模擬）
      │
      ├─ 全綠 → 允許觸發 Vercel production
      └─ 任一紅 → 阻止 release + 通知開發者
```

### 6.2 品質門檻的紀律

| 紀律 | 說明 |
|------|------|
| **強制** | 非「可選」，失敗即擋 |
| **可稽核** | 保留 log，知道為什麼擋 |
| **更新** | 新增需求時同步更新檢查項 |
| **人工覆核** | 誤報需人工判斷，不全自動放行 |

> **關鍵**：QA Gate 是「守門員」而非「橡皮圖章」——它攔住明顯問題，同時保留人類對模糊結果的最終判斷。

## 7. 誤報與維護：品質門檻也會生病（~300 字）

### 7.1 誤報來源

| 誤報 | 原因 | 處置 |
|------|------|------|
| CSS/JS 含 'error' 字樣 | 掃描字串誤判 | 人工判斷是否為使用者可見錯誤 |
| Browserbase 偶發逾時 | 網路/環境波動 | 重跑或標記環境因素 |
| 錯誤字串出現在非使用者區 | 過度嚴格的 regex | 精準化掃描範圍 |

### 7.2 維護成本
- 測試腳本需隨功能演進同步更新
- 誤報會降低信任 → 需讓「綠燈」可信

### 建議
- 定期檢視誤報率、調整掃描規則
- 把「錯誤字串」定義成**使用者可見**前提，減少誤判
- 紀錄過去的誤報案例作為規則庫

---

## 8. 實際成效與避坑（~300 字）

### 實際成效
- **攔截大量「未登入可存取管理頁面」類問題**（資安）
- 把部署前檢查從「人工點測 30+ 頁」降為「腳本重複跑」
- 建立「公開/受保護/DB/Middleware/API/表單」六大維度的通用品質框架

### 避坑清單

| 坑 | 解法 |
|----|------|
| 只信任 curl 狀態碼 | 加上 Browserbase 真瀏覽器模擬 |
| 錯誤字串 rule 過度嚴格 | 定義「使用者可見」前提 + 人工覆核 |
| 測試不改 | 功能演進時同步更新檢查項 |
| 綠燈不值錢 | 確保 test 真的覆蓋到關鍵路徑 |

## 9. 總結與可複製模板（~200 字）

### 核心原則
1. **品質門檻 = 固定、可稽核、每次強制跑**，而非靠感覺
2. **多維度檢查**（build / HTTP / DB / Middleware / API / 表單）涵蓋使用者真實遇到的情境
3. **真瀏覽器模擬**補足 curl 狀態碼看不到的互動層
4. **誤報可管理**（精準規則 + 人工覆核），維持綠燈可信
5. **可累積**，每跑一次都是工程資產

### 可複製檢查清單
```
☐ Build 成功（無 TS/lint error）
☐ 公開頁 HTTP 200
☐ 受保護頁未登入 → 307
☐ DB 表格齊全
☐ Middleware 路由正確
☐ 未登入 API → 401
☐ 表單 try/finally + disabled
☐ 瀏覽器使用者模擬（訪客/後台/跑者）通過
☐ 無「使用者可見錯誤」字串
```
